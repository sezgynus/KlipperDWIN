# Maintenance Stage 8B — bounded actuator program compilation

[Türkçe](maintenance-pulse_TR.md)

This is a **pure compiler**: no method here sends commands, starts tests, claims hardware PASS, or bypasses safety. Only exact USER-guided discovery rows can produce an immutable `PulseProgram`. The generated G-code has one allowlisted stimulus, a 150–950 ms `G4` delay and an explicit original-state restoration in **one bounded script**. Start is forbidden if original firmware status is missing or untrusted. External clients and Klipper restarts can still interrupt scripts: a subsequent executor MUST independently verify the restored output before reporting that restoration was observed.

Hardware profiles: F01 part fan uses M106 and restores prior commanded PWM, not RPM; F04 fan_generic uses exact SET_FAN_SPEED and refuses templates or unsafe names; O03 is any explicitly registered visual output_pin PWM with scale 1, a live baseline and raw config pin identity; O04 is a single LED element with fully known color_data and exact SET_LED restore, not multi-pixel strips; S18 is a per-device, explicitly registered audible pwm_cycle_time output with configured default and shutdown value 0 (not live OFF telemetry). Unsupported hardware remains blocked. Klipper's G-code command grammar is documented in its official [G-Codes reference](https://www.klipper3d.org/G-Codes.html).

The future executor must keep the printer idle, verify Moonraker job queue and other Petrel operations, guard the dispatch, avoid automatic execution on UI/menu entry, read the target again after completion, distinguish physical user-observed YES/NO from status values, and preserve INCONCLUSIVE if verification fails. All tests are run only in GitHub CI.

## S18 readback limitation

The opt-in `pwm_cycle_time` buzzer has no Klipper status readback. Its bounded script first commands OFF, waits 50 ms, sends a 150-ms tone, and commands OFF again. The 200-ms program **attempts** restoration but does not establish that it physically occurred; `restored()` deliberately never accepts S18 as telemetry-verified, even when handed a fabricated status value. Only the exact explicitly permitted, default-OFF effective configuration is admitted.

The S18/O03 SET_PIN compilers require a separately verified case-preserved `pin_command_name` from Klipper's raw configuration. It rejects missing or case-insensitively different identifiers, and uses only this validated spelling for every `SET_PIN PIN=` command.

## O04 indexed LED chains

O04 supports a bounded **1–32 pixel** uniformly RGB or RGBW LED chain from a positively discovered and separately opted-in Klipper `led`, `neopixel`, `dotstar` or `pca9632` object. The live `color_data` must contain one valid 4-channel record for every physical LED, exactly matching the effective `chain_count` (default 1). A short 750-ms color change is compiled **for each 1-based INDEX**. `TRANSMIT=0` batches all but the last indexed command; the final `TRANSMIT=1` transmits the complete changed or restored frame. Restoration sends each pixel's *own* full original color. Only two consecutive full-chain status matches after the bounded script, followed by the operator's observation, can yield `PASSED_USER`. A partial, missing, stale, NaN or different chain is never accepted.

**Ownership:** Klipper's `mmu_leds`/`led_effect` controllers can continue writing LEDs while the printer/MMU is idle. If effective configuration references the selected chain from an `mmu_leds`, `led_effect`, `_led_effect` or `mmu_led_effect` section, O04 refuses execution at preflight. It does not turn off Happy Hare, cancel animations or silently steal an LED chain. The next integration step is an explicit, verified handoff/release protocol for managed chains; merely assigning a `led` profile is not permission to bypass an independent controller. Chains longer than 32, mixed RGB/RGBW layouts, unknown pixel counts and unverified baselines are deliberately blocked.

## Happy Hare-owned O04 chains: native timed API

For an explicitly profiled physical LED chain wholly and exclusively mapped to a single `[mmu_leds unit]` **exit** segment (e.g. `neopixel:... (1-N)`), Petrel uses `MMU_SET_LED UNIT=<validated-unit> EXIT_EFFECT=(0,0.35,0) DURATION=1 FADETIME=0`. This does **not** disable Happy Hare, bypass the MMU LED owner or issue `SET_LED` directly. Happy Hare's internal one-second transient timer returns the unit to its current default LED policy even if the Petrel screen stops updating. Invalid mappings, incomplete chain ownership, disabled MMU LEDs, busy MMU actions and independently owned physical effects are refused before dispatch. The usual explicit double consent and live safety dispatch guards remain mandatory.

The runner checks that Happy Hare still reports the original `enabled` and `animation` settings after the bounded duration, with two status reads. These stable control settings **do not prove** the dynamic LED color restored or the internal timer ran, so the UI only records `OBSERVED_USER` on an affirmative physical observation, **`restore_verified=False`**. A real-hardware O04 acceptance remains pending. For standalone, *unmanaged* LED chains the original indexed full-color restoration and `PASSED_USER` behavior is unchanged. This native approach is preferred to `MMU_LED ENABLE=0`, which can leave ownership disabled after an interrupted multi-request handoff.
